# AI Quality Evaluation Demo

A small, reproducible test harness that evaluates the answers of an AI help assistant against a versioned dataset, written in Python with Behave (BDD).

> **Independent demonstration project.** This is personal work built with synthetic data. It is not employer work, it does not use any employer code or data, and it does not call a real model. "DemoWallet" is a fictional product, and every name, email, number and secret in `data/` is invented.

## What it shows

AI assistants fail in ways that ordinary `assert status == 200` tests don't catch. This harness checks seven kinds of behaviour, each with explicit expected behaviour recorded in the dataset:

| Category | Question it asks | Check used |
|---|---|---|
| Correctness | Does the answer state the required facts? | `includes_all`, `excludes_all` |
| Grounding | Is every claim supported by the supplied source? | `grounded` (word overlap), `numbers_grounded` |
| Unanswerable questions | Does it admit when the source has no answer instead of inventing one? | `acknowledges_unknown` |
| Prompt injection | Does it ignore instructions hidden in untrusted content? | `excludes_all` on a canary token |
| Privacy | Does it keep restricted records, secrets and contact details out of answers? | `no_sensitive_data` (regex) |
| Robustness | Does it clarify ambiguous input and correct false premises? | `asks_clarification`, `includes_all` |
| Regression | Did a new build get worse than the reference build? | report diff (`--compare`) |

Two recorded builds are evaluated:

- **`baseline`**: the reference build, with well-behaved answers.
- **`candidate`**: a hypothetical new build with seven deliberately planted defects (a made-up price, a leaked synthetic secret, an obeyed injected instruction and so on). The harness has to catch every one.

## Project layout

```
data/
  knowledge_base.json      synthetic source articles (v1.0.0), incl. one untrusted and one restricted doc
  cases.json               evaluation dataset (v1.0.0): question, context, expected behaviour, checks
  responses/baseline.json  recorded answers from the reference build
  responses/candidate.json recorded answers from a regressed build
aiqe/
  checks.py                deterministic check functions
  evaluate.py              scoring, regression diff, JSON + Markdown reports, CI exit code
features/                  Behave scenarios: quality gate, regression detection, known limitations
reports/                   example output generated by the commands below
```

Test data is kept separate from the evaluation logic. A case only names which checks apply and with which parameters.

## Run it

Requires Python 3.10+.

```bash
pip install -r requirements.txt

# BDD suite: quality gate, regression detection, documented limitations
behave

# Scored reports (JSON + Markdown) in reports/
python -m aiqe.evaluate --build baseline
python -m aiqe.evaluate --build candidate --compare reports/baseline.json
```

`aiqe.evaluate` exits with code 1 when any case fails, so it can gate a pipeline. On the candidate build that is the expected result.

## Limitations of automated judging

These checks are deterministic heuristics. They make results reproducible and cheap to run on every change, but they are not semantic understanding. The dataset records two cases on purpose, and the reports show them separately instead of counting them as passes:

- **Known false positive (`LIM-001`).** A correct paraphrase ("Holders don't pay anything to check a credential") shares too few words with the source, so the `grounded` check flags it.
- **Known false negative (`LIM-002`).** A wrong answer ("support staff can see and reset the recovery phrase") reuses the source's own words, so word overlap passes it. Only an explicit `includes_all: ["never"]` check would catch it.

Other limits worth stating plainly:

- Passing this suite does not show that an assistant is safe, unbiased or free of hallucinations. It shows that it behaved as expected on these 13 cases.
- The regex privacy check only finds patterns it knows about. A secret in an unexpected format would get through.
- The responses are recorded by hand to model the two builds. No live model is called, so results are fully reproducible but say nothing about any particular model.
- Thresholds (for example `min_overlap: 0.6`) were chosen for this dataset and would need tuning for another one.

## Evaluating a real assistant

To score a real system, save its answers in the same shape as `data/responses/baseline.json`, then run `python -m aiqe.evaluate --build <name>`. Keep API keys in environment variables and out of the repository. A model-graded check (LLM-as-judge) could be added as an optional extra, but it needs its own validation set, because the judge can be wrong too.

## Design decisions

- **Recorded responses instead of live calls**, so every run is reproducible and the demo needs no paid API.
- **Versioned dataset and knowledge base.** The evaluator refuses to run when the dataset expects a different knowledge-base version.
- **Behave for the acceptance layer.** Scenarios read as test intent ("Makes up a price"), while the Python checks stay plain functions that are easy to unit test.
- **Known limitations are classified, not hidden.** `known_false_positive` and `known_false_negative` are their own outcomes in every report.
